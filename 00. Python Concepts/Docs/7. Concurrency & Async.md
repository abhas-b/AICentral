## The one decision that matters: what kind of work is it?

Concurrency has three tools in Python, and picking the right one is almost entirely
determined by **what's slow**:

| Your bottleneck | Use | Why |
|---|---|---|
| **I/O-bound** (network, disk, DB, APIs) — waiting on other systems | **threads** or **asyncio** | while one task waits, others run; no CPU contention |
| **CPU-bound** (math, parsing, crunching) — burning the processor | **multiprocessing** | only separate processes get true parallelism (bypass the GIL) |
| **Very high-concurrency I/O** (thousands of connections) | **asyncio** | one thread, cooperative, far lighter than thousands of OS threads |

- **Concurrency** = dealing with many things at once (structure). **Parallelism** = doing
  many things at literally the same instant (execution). Threads/async give concurrency;
  only multiprocessing (or multiple machines) gives CPU parallelism in CPython.
- The classic mistake is throwing threads at CPU-bound work (they won't help — you'll see
  why) or reaching for processes on I/O-bound work (needless overhead).

Everything below elaborates this table.

## 1. The GIL — why the model matters

CPython has a **Global Interpreter Lock**: only one thread executes Python bytecode at a
time. It exists to make memory management (reference counting) safe and simple. The
consequence: **threads don't parallelize CPU-bound Python code.**

But — crucially — the GIL is **released during blocking I/O** (and inside many C
extensions like NumPy). So while a thread waits on a socket or `time.sleep`, other threads
run. That's why threads *do* help I/O-bound work.

**Measured (single core):**

```
CPU-bound  sequential: 1.917s  |  2 threads: 1.908s   -> threads do NOT help (GIL)
I/O-bound  sequential: 2.002s  |  10 threads: 0.201s  -> threads HELP (10x)
```

Two threads on CPU work gave *zero* speedup (they take turns holding the GIL). Ten threads
on I/O work gave a **10×** speedup (they all wait concurrently — the waits overlap). This
single result is the whole reason the "what kind of work?" table exists.

> **The future:** Python 3.13 ships an experimental **free-threaded (no-GIL)** build
> (PEP 703) where threads *can* run Python in parallel, and **per-interpreter GIL** /
> subinterpreters (PEP 684/734) offer another isolation-based path. Both are maturing; for
> now, assume the GIL and design accordingly.

## 2. Threading

### The high-level way first: `concurrent.futures`

Don't start with raw `threading.Thread`. The modern, ergonomic API is
`concurrent.futures.ThreadPoolExecutor` — a pool of worker threads with a clean interface:

```python
from concurrent.futures import ThreadPoolExecutor, as_completed
import urllib.request   # any blocking I/O

def fetch(url):
    return len(urllib.request.urlopen(url).read())

urls = ["https://example.com"] * 10

with ThreadPoolExecutor(max_workers=10) as pool:
    # map: results in input order
    sizes = list(pool.map(fetch, urls))

    # or submit + as_completed: handle results as they finish
    futures = [pool.submit(fetch, u) for u in urls]
    for fut in as_completed(futures):
        size = fut.result()      # re-raises any exception from the worker
```

- `submit(fn, *args)` returns a **`Future`** — a handle to a result that isn't ready yet.
  `.result()` blocks until it is (and re-raises exceptions).
- `map(fn, iterable)` is the parallel `map`, results in order.
- `as_completed(futures)` yields futures as they finish — process fast ones first.
- The `with` block waits for all work and cleans up the pool.

**The beauty:** switch to `ProcessPoolExecutor` and the *same code* runs on multiple
processes. Reach for `concurrent.futures` before raw threads or processes.

### Raw threads and shared-state hazards

Under the hood, a thread is `threading.Thread(target=fn); t.start(); t.join()`. The danger
with threads is **shared mutable state**. When two threads do `counter += 1`, that's
actually *read, add, write* — three steps — and another thread can interleave, losing
updates. This is a **race condition**:

```python
counter = 0
def work():
    global counter
    for _ in range(1_000_000):
        counter += 1      # NOT atomic: read, +1, write
# 4 threads doing this can produce < 4,000,000
```

Races are **nondeterministic** — that's what makes them vicious. On this single-core
sandbox with the GIL, the unsynchronized counter happened to come out correct across runs;
on multi-core machines lost updates appear readily. **Never rely on "it worked on my
machine"** for shared-state correctness. The fix is a **lock**:

```python
import threading
counter = 0
lock = threading.Lock()

def work():
    global counter
    for _ in range(1_000_000):
        with lock:            # only one thread in this block at a time
            counter += 1
# -> reliably 4,000,000  (measured: correct)
```

### The synchronization toolkit

| Primitive | Use |
|---|---|
| `Lock` | mutual exclusion — one thread in a critical section |
| `RLock` | reentrant lock — same thread can acquire it multiple times |
| `Semaphore(n)` | allow up to *n* concurrent holders (bound a resource) |
| `Event` | one thread signals, others wait for a flag |
| `Condition` | wait for a condition + notify (producer/consumer) |
| `queue.Queue` | thread-safe hand-off — usually **better than sharing state** |
| `threading.local()` | per-thread storage (each thread sees its own value) |

**The best synchronization is often none** — instead of sharing mutable state behind locks,
pass data through a `queue.Queue`, which is thread-safe by design:

```python
import queue, threading

q = queue.Queue()

def producer():
    for i in range(5):
        q.put(i)
    q.put(None)          # sentinel: "done"

def consumer():
    while (item := q.get()) is not None:
        print("got", item)

threading.Thread(target=producer).start()
threading.Thread(target=consumer).start()
```

Locks are error-prone (forget one → race; acquire two in the wrong order → **deadlock**).
Prefer queues and immutable data; use locks only for genuinely shared mutable state, and
always via `with lock:` so they're released even on exceptions.

## 3. Multiprocessing — real CPU parallelism

For CPU-bound work, sidestep the GIL by using **separate processes**, each with its own
interpreter and GIL. Same high-level API, different executor:

```python
from concurrent.futures import ProcessPoolExecutor

def cpu_task(n):
    return sum(i * i for i in range(n))

with ProcessPoolExecutor() as pool:          # defaults to os.cpu_count() workers
    results = list(pool.map(cpu_task, [3_000_000] * 4))
```

**Measured here (single core):** sequential `0.593s` vs process pool `0.580s` — essentially
no gain, *because there's only one core to spread across*. On a machine with N cores,
CPU-bound work like this scales close to N× (4 jobs on 4 cores ≈ 4× faster). The process
pool can only parallelize if there's hardware to parallelize onto.

Costs and constraints to respect:

- **Startup + IPC overhead**: spawning processes and moving data between them isn't free.
  Only worth it when each task does substantial CPU work.
- **Pickling**: arguments and return values are **pickled** to cross process boundaries — so
  they must be picklable (no lambdas, open sockets, etc.), and large data transfers are
  costly. For big arrays, use `multiprocessing.shared_memory` to avoid copying.
- **The `__main__` guard**: on spawn-based platforms you **must** wrap the entry point:

```python
if __name__ == "__main__":       # required, or child processes re-import & re-run everything
    with ProcessPoolExecutor() as pool:
        ...
```

Omit that guard and you can get infinite process spawning. Always include it in scripts that
create processes.

## 4. asyncio — concurrency on a single thread

`asyncio` gives high concurrency **without threads or the GIL fight**, by running many tasks
cooperatively on **one thread**. This is `yield`-based coroutines (tutorial 3 §4) grown into
a full framework.

### The mental model

- An **event loop** runs on one thread and juggles many coroutines.
- `await` marks a **suspension point**: "I'm about to wait — loop, go run something else, and
  resume me when this is ready." Between `await`s, a coroutine runs uninterrupted (no races
  on its own state — that's a real simplicity win over threads).
- Because it's cooperative and single-threaded, asyncio scales to **thousands** of concurrent
  I/O operations cheaply, where thousands of OS threads would be too heavy.

```python
import asyncio

async def fetch(i):          # a coroutine (async def)
    await asyncio.sleep(0.2) # models awaiting I/O; yields control to the loop
    return i * 10

async def main():
    result = await fetch(1)  # await pauses main until fetch(1) completes
    print(result)            # 10

asyncio.run(main())          # start the event loop and run main() to completion
```

Calling `fetch(1)` does **not** run it — it returns a coroutine object. It runs only when
`await`ed or scheduled as a task. This trips up everyone once.

### Running things concurrently: `gather` and `TaskGroup`

Awaiting one coroutine at a time is sequential. To run many *concurrently*, schedule them all:

```python
async def main():
    # gather: run all concurrently, collect results in order
    results = await asyncio.gather(fetch(1), fetch(2), fetch(3))
    print(results)   # [10, 20, 30]  — took ~0.2s total, not 0.6s
```

`asyncio.create_task(coro)` schedules a coroutine to run in the background immediately,
returning a **Task**. The modern, safer way to manage a group of tasks is **`TaskGroup`**
(3.11+), which waits for all of them and propagates errors cleanly:

```python
async def main():
    async with asyncio.TaskGroup() as tg:      # structured concurrency
        t1 = tg.create_task(fetch(1))
        t2 = tg.create_task(fetch(2))
    # on exit, all tasks are done; if any raised, they surface here as a group
    print(t1.result(), t2.result())
```

`TaskGroup` is preferred over bare `create_task` + `gather`: if one task fails, the others
are cancelled and errors are collected — no silently-dropped exceptions.

### Bounding concurrency with a Semaphore

Firing 10,000 requests at once will get you rate-limited or run you out of sockets. An
`asyncio.Semaphore` caps how many run simultaneously:

```python
async def bounded_fetch(sem, i):
    async with sem:               # at most N inside this block at once
        return await fetch(i)

async def main(limit=3):
    sem = asyncio.Semaphore(limit)
    return await asyncio.gather(*(bounded_fetch(sem, i) for i in range(10)))
```

**Measured:** 10 tasks of 0.2s each, unbounded → `0.201s`; bounded to 3 → `0.803s`
(exactly `ceil(10/3) × 0.2` — the tasks run in four waves). This is the standard pattern for
being a good client to an API or your broker.

### Timeouts and cancellation

```python
async def main():
    try:
        async with asyncio.timeout(0.1):     # 3.11+; cancels the block if it overruns
            await fetch(1)                    # fetch takes 0.2s -> times out
    except TimeoutError:
        print("timed out")

# Cancellation: task.cancel() raises CancelledError inside the coroutine
async def cancel_demo():
    task = asyncio.create_task(fetch(1))
    await asyncio.sleep(0.05)
    task.cancel()                             # request cancellation
    try:
        await task
    except asyncio.CancelledError:
        print("cancelled")
```

Handle `CancelledError` to clean up (close files/connections), then usually re-raise it.

### The cardinal sin: blocking the loop

Because everything shares one thread, a single **blocking** call freezes *every* task. Never
put `time.sleep`, heavy CPU, or a synchronous network library inside a coroutine:

```python
async def bad():
    time.sleep(1)          # ❌ FREEZES the entire event loop for 1s
    requests.get(url)      # ❌ blocking HTTP library — blocks all tasks

async def good():
    await asyncio.sleep(1) # ✅ yields to the loop
    # for a blocking library you can't avoid, offload it to a thread:
    loop = asyncio.get_running_loop()
    await loop.run_in_executor(None, blocking_function, arg)  # runs in a thread pool
```

`run_in_executor` is the bridge: it moves blocking/CPU work off the event-loop thread so the
loop stays responsive. Use async-native libraries (`httpx`, `aiohttp`, async DB drivers)
throughout, or offload the stragglers.

### Async generators, async context managers, `contextvars`

```python
# async generator: yield inside an async def, consumed with `async for`
async def stream(n):
    for i in range(n):
        await asyncio.sleep(0.01)
        yield i

async def consume():
    async for item in stream(3):     # async iteration
        print(item)

# async context manager: __aenter__ / __aexit__, used with `async with`
# (async DB connections, locks, sessions all use this)

# contextvars: like thread-local, but correct across async tasks
import contextvars
request_id = contextvars.ContextVar("request_id", default="-")
# each task gets its own value; safe where thread-local would leak across tasks
```

`contextvars` is the async-safe answer to "per-request context" (e.g. a request/trace ID
threaded through a call chain) — thread-locals don't work correctly with asyncio tasks.

## 5. Choosing, and the wider ecosystem

**Decision recap:**

- **I/O-bound, modest scale, or must call blocking libraries** → **threads**
  (`ThreadPoolExecutor`). Simple, preemptive, works with any library.
- **I/O-bound, high scale, or building a server/agent** → **asyncio**. Lightest for
  thousands of concurrent waits — *if* your whole stack is async-aware.
- **CPU-bound** → **multiprocessing** (`ProcessPoolExecutor`). The only real parallelism;
  worth the overhead only for substantial CPU work on a multi-core machine.

**Ecosystem awareness:**

- **`anyio`** / **`trio`** — libraries built around *structured concurrency* (asyncio's
  `TaskGroup` borrowed the idea). `anyio` runs on top of asyncio and is worth knowing if you
  build async libraries.
- **Async pitfalls to remember:** never block the loop; don't mix sync and async carelessly;
  one blocking call in the chain ruins the concurrency; always bound outbound concurrency.
- **Subinterpreters / free-threading** (3.12–3.13+): emerging models that may eventually let
  a single process use multiple cores for Python code without separate OS processes. Keep an
  eye on them; design for today's GIL for now.

## Milestone Project — the same task, three ways, measured

Implement one I/O-bound task **three ways** and a CPU-bound variant, then compare — the
exercise that builds real intuition for the decision table. The reference was **run**; the
numbers are real.

Requirements:

1. An I/O task (modeled by a 0.2s wait), 10 units, via **`ThreadPoolExecutor`**.
2. The same via **`asyncio.gather`** (and `TaskGroup`).
3. A **`Semaphore`**-bounded async version (limit 3) — observe the wave behavior.
4. A CPU-bound variant via **`ProcessPoolExecutor`** vs sequential.

<details><summary>Reference solution (measured output)</summary>

```python
import asyncio, time, os
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

UNITS, DELAY = 10, 0.2

def blocking_io(i):
    time.sleep(DELAY);  return i

async def async_io(i):
    await asyncio.sleep(DELAY);  return i

# (1) threads
def run_threads():
    with ThreadPoolExecutor(max_workers=UNITS) as ex:
        return list(ex.map(blocking_io, range(UNITS)))

# (2) asyncio, all at once
async def run_gather():
    return await asyncio.gather(*(async_io(i) for i in range(UNITS)))

# (3) asyncio, bounded to 3 concurrent
async def run_bounded(limit=3):
    sem = asyncio.Semaphore(limit)
    async def guarded(i):
        async with sem:
            return await async_io(i)
    return await asyncio.gather(*(guarded(i) for i in range(UNITS)))

# (4) CPU-bound: sequential vs processes
def cpu_task(n):
    return sum(i * i for i in range(n))

if __name__ == "__main__":
    for label, fn in [
        ("ThreadPoolExecutor", lambda: run_threads()),
        ("asyncio.gather",     lambda: asyncio.run(run_gather())),
        ("asyncio+Semaphore(3)", lambda: asyncio.run(run_bounded(3))),
    ]:
        t0 = time.perf_counter(); fn()
        print(f"{label:22}: {time.perf_counter()-t0:.3f}s")

    M, JOBS = 3_000_000, 4
    t0 = time.perf_counter(); [cpu_task(M) for _ in range(JOBS)]
    print(f"{'CPU sequential':22}: {time.perf_counter()-t0:.3f}s")
    t0 = time.perf_counter()
    with ProcessPoolExecutor() as ex:
        list(ex.map(cpu_task, [M]*JOBS))
    print(f"{'CPU ProcessPool':22}: {time.perf_counter()-t0:.3f}s   (cores={os.cpu_count()})")
```

**Measured output (single-core sandbox):**
```
I/O serial baseline ~= 2.0s
ThreadPoolExecutor    : 0.201s
asyncio.gather        : 0.201s
asyncio+Semaphore(3)  : 0.803s   (~ceil(10/3)*0.2 = 0.8s)
asyncio TaskGroup     : 0.201s
CPU sequential        : 0.593s
CPU ProcessPool       : 0.580s   (cores=1)
```

**Reading the results:**

- **Threads and asyncio both turned 2.0s of I/O into 0.2s** — a 10× win, because the ten
  0.2s waits *overlap*. For pure I/O at this scale they're equivalent; asyncio pulls ahead
  at much larger scale (thousands of tasks) where threads get heavy.
- **The Semaphore version took exactly 0.8s** — bounding to 3 concurrent means 10 tasks run
  in 4 waves (`ceil(10/3) = 4`, × 0.2s). Real proof of controlled concurrency.
- **The process pool didn't beat sequential — because this box has 1 core.** On a 4-core
  machine, `CPU ProcessPool` would drop to roughly `0.593 / 4 ≈ 0.15s`. The mechanism is
  correct (work spread across processes, GIL bypassed); it just needs cores to pay off.

**Stretch goals:**
- Replace the sleep with real HTTP using `httpx.AsyncClient` (async) and `requests`
  (threads); observe the same shape with real latency.
- Add `run_in_executor` to call the *blocking* version from inside asyncio.
- Add a `TaskGroup` version with one task that raises, and see how errors propagate.
- Re-run the CPU test on a multi-core machine and confirm the near-linear speedup.
